## What This Product Is

Provenance is a local-first agent control plane with a browser dashboard and a trusted TypeScript kernel. The kernel owns goals, evidence, budgets, approvals, memory, skills, provider calls, capability dispatch, automations, research mission checkpoints, authenticated report artifacts, recovery, snapshot commits, desktop action authority, diagnostics, and release records. Models propose content and actions; deterministic policy and explicit human authority decide what can persist or execute. A Windows Tauri/Rust host supplies bounded process supervision, first-run authority onboarding, UI Automation, and a release-only signed update path, but does not replace the TypeScript policy authority.

Multi-user authentication exists, but users share one local kernel state. The product is therefore a loopback-oriented local deployment, not a hardened multi-tenant service.

## Security-Critical Flows

### Application AI

`/api/chat`, `/api/extract`, `/api/mutate`, and `/api/self-improve` pass through the application AI router, the configured provider policy, kernel provider-call accounting, ledger evidence, and the unified mutation access guard. Provider results include route provenance. Extraction creates candidates; it does not promote memory.

### Skill evaluation

Skill candidates bind an authenticated principal and a pre-existing evaluation-suite id/hash. Suite creation accepts only a source id. A configured resolver must return a hash-sealed source from an allowlisted evaluator; the kernel records its attestation before the suite seal and later candidate event. Caller-supplied oracle content, authority claims, legacy suites, same-author evaluation, and training/held-out overlap by case id, input fingerprint, or source event fail closed. Suite and evaluation APIs expose metadata only, while canary expected outputs remain kernel-private. The standard server intentionally has no default evaluator resolver.

### Research missions

The Research Missions cockpit creates a kernel-owned five-stage DAG: plan, collect, synthesize, verify, and publish. Seed URLs must be unique canonical HTTPS URLs whose origins are already in `WEB_INSPECT_ORIGINS`. The provider cannot add a URL, call a tool, or change mission authority. Collection uses only `browser.inspect` at L0, blocks redirects, pins the requested/final origin, and stores bounded source text in authenticated artifacts. Prompt-injection assessment may quarantine a source; a quarantined source is excluded from synthesis and critique.

Plan, synthesis, and a separate critique pass use the configured provider router, goal budget, structured schemas, route evidence, and a 60-second provider timeout. Separate means another request and stage, not necessarily another provider or model. Deterministic verification re-resolves artifact and chunk hashes, requires each quotation to be a specific exact excerpt of at least 20 characters and three words, and requires distinct origins and content hashes for high confidence. Publication occurs only after those checks and a passing critique; dynamic Markdown/HTML is escaped. The report endpoint rechecks the authenticated publication inputs, each source artifact and reconstructed chunk map, the cited source/provider/verification ledger events, and the final report artifact before returning content.

Each external step records an active checkpoint before dispatch. Concurrent step requests observe `in_progress` rather than dispatching twice. Stop All aborts active provider and source controllers and prevents result commit. On restart, uncertain in-flight work is recovered as blocked; only retryable failures can resume, and the operator must provide a reason recorded as mission and task evidence. Bounded grounding retries stop after three synthesis attempts.

When operator-token or multi-user access control is configured, every authoritative `/api/kernel` GET except the sanitized runtime capability report requires a valid bearer credential. Multi-user viewers may read mission state; mission mutations remain limited to admin/operator sessions. Sanitized auth, provider, core-model, and runtime status endpoints stay public for login-time availability reporting. In loopback-only `open` mode, reads and mutations are available without a bearer because no access mechanism is configured.

### Durable recurring research

The Schedules cockpit creates interval-only contracts for the bounded report mission. The objective and one to five canonical allowlisted HTTPS sources are fixed, authority is derived as read-only L1 with no side effects, schedules begin disabled, and updates cannot increase scope, frequency, or budgets. Intervals range from 15 minutes through 365 days. `latest_once` catch-up claims only the newest missed boundary and records the skipped count.

Under the mutation queue of one trusted kernel process, the kernel rechecks current source origins and atomically persists the deterministic occurrence id, run-budget charge, goal, mission, tasks, deadline, owner lease, and fence before dispatch. Provider and source I/O run outside that queue. Concurrent ticks see the active occurrence; stale owners and fences cannot commit. Every result write rechecks ownership, Stop All, deadline, and lease expiry. Completion requires the ordinary report authentication chain and a publication acceptance time before the persisted deadline; the occurrence stores its artifact id and content hash. Runtime and source-fetch usage accumulate across explicit retries.

Stop All and shutdown abort active recurring work; provider, worker, and optional observation-assessor awaits are abort-bounded even for non-cooperative adapters. Graceful scheduler shutdown waits at most 10 seconds before detaching a stale tick generation. Startup first authenticates and migrates the snapshot, then turns incomplete claimed/running occurrences into uncertain blocked checkpoints without replay. A fully authenticated report published before the occurrence deadline can instead be reconciled to completed. Recovery calls coalesce while recovery is already running and reject with conflict while any live external dispatch owns the process; they cannot reclassify an executing occurrence. Otherwise an operator must explicitly resume under a fresh lease/fence within the remaining cumulative budgets or skip with a reason. Protected schedule reads allow viewers; create, enable/disable, tick, resume, and skip require operator/admin authority. The main server clock is recursive and non-overlapping; release-child processes do not start it.

### Browser automation

`browser.inspect` remains L0. Navigation, clicking, typing, and any future download operation have an L2 minimum. The write context blocks off-origin top-level requests before dispatch, rejects redirects and script navigation, closes unexpected pages, disables accepted downloads, and cancels/deletes any download triggered by click or typing. Approval-gated runs can resume only with their matching approved record. The persisted capability grant is consumed before worker I/O. Explicit `browser.download` remains unavailable.

### Production desktop runtime

The Windows host selects a per-user local application-data runtime outside the command workspace, owns it before starting the control plane, and supervises only the canonical `dist/server.cjs` entrypoint through an exactly packaged `node.exe`, a minimal environment, a per-launch readiness proof, and a kill-on-close job. Packaged builds embed a canonical resource manifest; startup authenticates declared paths, sizes, and hashes, rejects undeclared, reparse-point, or non-regular entries in the exact `dist` inventory, and retains file handles for the supervised lifetime. Node accepts only the locked manifest copy published by Rust and serves only its authenticated index and asset entries; complete installed-tree inventory verification remains a protected-workflow gate. The owner record contains the host PID and SHA-256 hash of a private proof passed only to the child; copying the public record cannot authenticate a second Node process. Standalone Node keeps its compatible repository-local default and atomic owner record. This prevents ordinary competing launches from sharing one runtime; it does not make the process-local kernel queues suitable for high availability.

A packaged first launch asks the operator to select and confirm 1-32 executable identities and a project workspace containing a non-symlink `package.json`. Those selections are persisted under native per-user configuration. Invalid records are quarantined before reconfiguration, and the selected workspace must be disjoint from packaged resources, runtime state, and configuration. Packaged releases ignore environment-provided allowlist/workspace authority; development launches retain explicit environment overrides.

For a fresh per-user runtime, Rust generates a URL-safe one-launch first-admin secret, passes it only through the supervised child's minimal environment, and places it in the initial webview URL fragment. The dashboard removes the fragment from URL/history immediately, retains the value only in memory, and sends it only on the dedicated first-admin request. Node deletes the environment value at startup. While this authority is pending, the shared API guard is closed except for auth status and first-admin creation; the secret is consumed only after the administrator is durably created. Bootstrap then logs in and moves the running process to `multi_user`. Node rechecks bridge health and activates the already registered desktop runtime without restart. Activation may change availability only: the registry rejects any change to worker identity, action/risk authority, or application allowlist. Failure remains closed, and a later valid login may retry activation.

The bridge binds only to `127.0.0.1` on an ephemeral port. A per-launch secret authenticates bounded request metadata, request id, timestamp, body hash, response status, and response body with HMAC-SHA256; consumed request ids cannot be replayed. Native acceptance uses a separate one-use token accepted only by a Rust-owned loopback endpoint after exact Host, Origin, and body checks; Node never receives that mount authority. Node enables the worker only after authenticated health matches the configured capabilities and exact application-id allowlist. All `DESKTOP_*` launch values and nonce-bearing variables are removed from command-worker environments.

Desktop execution is blocked unless the server is in `operator_token` or `multi_user` mode. An authenticated operator may run L0 `desktop.discover` and `desktop.inspect`; viewer sessions remain read-only at the API level. `desktop.click` and `desktop.type` are L2, so the first automation run creates an approval and only a later run with the matching approved record may reach one-use capability dispatch. Mutations bind app id, window id, tree revision, and node id. Typed text is resolved destructively from an expiring in-memory store, then its exact UTF-8 SHA-256 is verified again by the native host. UI Automation trees and window metadata remain untrusted observations and cannot confer authority.

Native availability is fail-closed: absent or partial launch settings, open access mode, health authentication failure, capability mismatch, allowlist mismatch, or a stale tree leaves the worker unavailable or blocks the action. The UIA broker uses bounded nonblocking admission and rechecks each request generation and deadline before side effects; queue-full, expired, or invalidated work does not mutate. It also rechecks window, PID, executable, tree path, and stable node identity immediately before mutation. Typing releases the pre-focus value pattern, focuses the control, rebuilds and revalidates the tree, and obtains a fresh pattern immediately before `SetValue`. Windows COM work that has already started cannot be cancelled safely. If a native mutation times out, may outlive cancellation, or cannot be re-observed, the kernel records `automation.run_uncertain` and refuses automatic retry. A broker-level timeout additionally marks UI Automation unhealthy. The host monitors Node, bridge, and UIA liveness and clears/closes the webview on loss; because the browser-facing port is still Node-owned rather than held by a Rust reverse proxy, exhaustive same-user port-rebinding resistance remains an external-audit item.

Command execution is independently fail-closed. Release planning requires a digest-pinned Docker image, and the native host passes only that embedded value to Node. Startup probes the Docker daemon and actually runs the image with the exact selected workspace mount. Native commands are disabled if any part of that probe fails, with denial occurring before one-use capability consumption. The trusted-host command fallback remains limited to standalone source runs and is explicitly reported as degraded.

The production bundle contains built web assets, the self-contained server entrypoint, JavaScript and Rust third-party notices, an exactly versioned and hashed Windows x64 Node executable with its expected vendor Authenticode signer/timestamp, and its separately hashed adjacent license. The no-secret build embeds the canonical manifest digest, rehashes the resources after native compilation, and refuses to stage a payload if the digest changed. Clean-resource smoke testing rejects unexpected external server imports and probes readiness, diagnostics, and unavailable optional features without repository `node_modules`. Installer v1 does not include a Playwright browser engine or the optional local `node-llama-cpp` runtime/model; those capabilities therefore remain unavailable in the installed build.

The isolated pilot package now carries that complete license and notice
inventory, and its sidecar records the exact license-resource and bundled-Node
hashes under the canonical resource-manifest digest. It is still an unsigned,
locally keyed, non-distributable test artifact: it does not satisfy the
production Node signer, Authenticode, updater-key custody, sandbox, attestation,
or protected-workflow gates.

Rust checks the configured HTTPS manifest with the configured public key, records only phase/current/candidate version, prompts through a native dialog, and shuts down the supervised child before updater exit. The remote dashboard page has no updater or dialog invoke permission. Check/install failure is an early fail-closed recovery boundary; there is no automatic rollback of the already installed trusted Tauri parent.

### Production desktop release

The verification/release contract pins CI Node.js `22.23.1`, Rust MSVC `1.97.0`, `@tauri-apps/cli` `2.11.4`, `cargo-about` `0.9.1` with exact archive/executable digests, and `spdx-expression-parse` `5.0.0`. The production Node runtime is separately selected by protected variables and must match its exact version, archive and executable hashes, x64/win32 identity, vendor signer/timestamp, adjacent license, and license hash. Release planning additionally binds `package-lock.json`, `Cargo.lock`, the generated notice hashes, updater public policy, and the digest-pinned Docker image.

The manual release workflow first runs a no-signing-authority Windows job. It installs locked JavaScript dependencies, fetches only `Cargo.lock`-resolved Rust dependencies before frozen license generation, runs the TypeScript/Rust/release/license and operational decision-replay gates, builds the self-contained resources and unsigned native, and uploads an exact-manifest-only unsigned payload with its manifest/native/resource-manifest/sign-command hashes. The protected `production` job is limited to `main` or a `v*` tag. Before secrets, it checks out the same revision, re-downloads the production Node distribution under distinct `PROVENANCE_PRODUCTION_*` values, revalidates the untouched payload and signing-script hashes, and selects a valid Microsoft-signed Windows SDK `signtool.exe`.

Every payload resource is copied into a fresh signed target and rehashed before and after bundling. Tauri's custom sign callback may mutate only the exact native executable, a constrained `nst????.tmp` NSIS uninstaller, and the exact setup executable. The manifest-bound, vendor-signed Node callback and five exact copied NSIS build plugins are verification-only no-ops. Tauri 2.11.4 changes exactly one native marker from `__TAURI_BUNDLE_TYPE_VAR_UNK` to `__TAURI_BUNDLE_TYPE_VAR_NSS` before the native callback, signs that file, and restores the original unsigned target after bundling. The callback uses create-new capture semantics to preserve the signed/patched native. The verifier permits only that marker replacement, PE checksum/security-directory changes, zero alignment padding, and one aligned EOF `WIN_CERTIFICATE`, and records the before/after hashes, marker offset, certificate hash/offset/size, signer, and timestamp.

The resulting bundle record binds the preserved unsigned payload, signed-native capture, signing command, production policy, and exact installer. After the PFX and imported certificate are removed, the workflow verifies public signatures, silently installs into a fresh directory, requires the installed native to be byte-identical to the capture, rehashes all installed resources against the unsigned manifest, verifies the installed uninstaller, and rejects extras/reparse points. Immediately before startup it revalidates the preserved payload again and supplies the immutable unsigned-job resource digest to installed-binary acceptance; only a passing authenticated shutdown may proceed to silent uninstall. Only then is the updater key exposed to sign the installer and bundle record. The exact public release set has four files: the setup executable, its `.sig`, `latest.json`, and `release-attestation.json`. The canonical bundle record and its signature are embedded as evidence rather than published as mutable side files. Publication separately requires an explicit protected `publish` choice and a matching immutable `v<version>` tag.

### Diagnostics

`GET /api/kernel/diagnostics` returns a no-store coded snapshot to authenticated viewers/operators in protected modes. It contains bounded build/runtime metadata, aggregate component states, and counts, not credentials or stored kernel payloads. `POST /api/kernel/diagnostics/support-bundle` requires operator/admin mutation authority in protected modes, persists the output through the kernel artifact store, and returns a bounded JSON attachment with SHA-256 integrity. Loopback `open` mode keeps the product's documented no-bearer behavior. Sensitive keys and authoritative strings become fixed reason markers or keyed correlation hashes; paths and unsupported values are never emitted. Bundle verification checks safe-schema conformance and checksum integrity, not digital-signature authenticity.

### Persistence

Every committed snapshot has a canonical content hash referenced by ledgered prepare/commit events. Startup accepts only a matching primary or authenticated recovery copy, completes interrupted publication, and marks abandoned ledger tails. The snapshot is authenticated by the ledger; domain-event payloads are not claimed to form a complete replay database. This is local integrity evidence, not non-repudiation, because the ledger has no external transparency anchor.

### Controlled Node-child releases

The Ed25519 signature binds target version, package hash, sorted evaluation references, and rollback instructions. Activation verifies the artifact and installed files, then starts only the declared controlled `.cjs` entrypoint with a fixed Node invocation and minimal environment. Windows requires the canonical native host helper: it creates the process suspended, assigns it to a new kill-on-close Job Object, resumes it only after assignment, and retains the job handle until exit. Readiness is an atomic, nonce-bound file whose version/hash/PID are authenticated; POSIX retains IPC readiness and a detached process group. The previous supervised child remains active until commit. Candidate failure terminates the owned job/group and removes only the candidate; unconfirmed cleanup stays tracked and returns `rollback_failed`.

The trusted parent Express control plane remains stable and owns policy, signatures, and rollback. A signed child does not rewrite repository source, inherit arbitrary parent secrets, or hot-replace the parent listener.

This controlled child lifecycle is separate from the native Tauri updater. Its pre-commit candidate rollback must not be presented as rollback of the installed Tauri parent.

## What Is Still Missing

- Native non-Docker command isolation. Packaged commands are disabled instead of falling back to the host.
- Representative Windows UI Automation validation across real third-party allowlisted applications and an external interactive security assessment. The CI Win32 fixture is controlled evidence, not broad product acceptance.
- Real protected `PROVENANCE_PRODUCTION_*` values, Authenticode certificate/PFX, updater signing key, production Node distribution/license, pinned production Docker image, timestamp service, and protected release approval. The repository contains the fail-closed pipeline, not those authorities.
- An actually executed signed release, retained protected-workflow evidence, hosted and independently fetched `latest.json`, and published four-file release set.
- Automatic rollback of the installed trusted Tauri parent after an updater failure.
- Desktop shortcuts, elevation, unrestricted shell authority, plugins, OAuth connector workers, and browser downloads.
- A production independent skill-evaluator resolver and allowlist. The kernel contract exists and fails closed, but the standard server ships no evaluator trust root or held-out dataset.
- Generic web search, source discovery, crawling, redirect following, and autonomous expansion beyond operator-supplied research seed URLs.
- Generic cron/event scheduling or recurring command, connector, email, communications, download, and desktop missions; the durable scheduler currently runs only fixed-source research reports.
- Multi-process ownership of one runtime directory; exactly one trusted parent server may own a given `.agent-kernel` because mutation and ledger queues are process-local.
- Live macOS/Linux vault verification.
- Per-user goal/memory partitioning and SSO/OIDC.
- Stable-port reverse proxying or an external blue/green cutover that replaces the trusted parent control-plane process.
- Arbitrary shell authority or arbitrary autonomous core self-modification; both are intentionally outside the security model.
- Installer telemetry policy and operating service, representative-machine installer/update/UIA acceptance, and an independent external security audit with resolved or accepted findings.

## Configuration-Dependent Status

The public sanitized runtime capability report is the source of truth for local availability; it does not return credentials or authoritative stored kernel objects. The richer diagnostics routes follow the unified access guard: authenticated roles in protected modes and loopback no-bearer access in explicitly configured `open` mode. Provider calls become available only when a supported server-side credential is configured. Research missions and their recurring scheduler additionally require the authenticated artifact store, the read-only inspection worker, and at least one `WEB_INSPECT_ORIGINS` entry. Browser writes require an installed browser engine plus their separate origin allowlist; installer v1 intentionally omits that engine. Desktop requires Windows, first-admin completion or another protected access mode, confirmed native application/workspace configuration, launch credentials, and authenticated bridge health whose capability and app-id sets exactly match Node's fixed registration. Native command isolation requires the release-pinned image plus a reachable Docker daemon and successful exact-workspace probe; command execution is unavailable otherwise. Controlled Node-child activation requires its separate verification key, signed authorization, evaluation references, and matching staged package. A signed NSIS build additionally requires all protected production inputs and the protected release workflow; publication and hosting are separate explicit steps. Unavailable integrations remain explicit instead of being simulated.
